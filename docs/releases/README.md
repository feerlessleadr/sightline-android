# Release notes

One file per release, named after its tag: `v0.1.0.md`, `v0.1.1.md` and so on. The release workflow refuses to publish a tag
without its file and puts the file's text at the top of the GitHub release, followed by the checksums.

Keep it short and in plain words: what is new, what changed, what is known not to work, and anything to do after updating.
Never put addresses, names or passwords in it: this repository is public.
